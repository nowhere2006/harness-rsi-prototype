# 反思：我们做的和论文做的差在哪

这份文档回答三个问题：TB2 和 TB4 到底在测什么不同的东西、我们的实现与 Evo-Harness 论文的流程差在哪、以及这个仓库目前能证明什么。

结论先放：**这一版不是论文的复现，是论文最小骨架的一次实现**。差别不在参数，在三个结构性的组件上。

## 1. Benchmark 层面：TB2 和 TB4 不是同一件事

| | TB 2.0 | TB 4.0 |
|---|---|---|
| 任务数 | 89 | 66 |
| Agent 超时 | 10–30 分钟 | 统一 **8 小时** |
| 验证方式 | 任务镜像内跑测试 | **独立 verifier 容器**，独立镜像 |
| 声明资源 | 1–2 核 / 2–4 GiB | 2–16 核 / 4–32 GiB |
| 镜像总量 | 45.6 GiB | 86.3 GiB |
| 专家耗时中位数 | 5–60 分钟 | **4 小时**（最长 60 小时） |
| 前沿模型通过率 | ~83%（2.1 版） | ~60% |
| DeepSeek Flash | ~83%（厂商口径） | 34–42% |

两套题侧重点不同：TB2 更偏"短任务里会不会正确使用工具"，TB4 把验证器隔离、时间放宽到 8 小时，测的是"长程任务里能不能自己推进、自己验证"。**分数不可跨版本比较。**

论文在 TerminalBench2 上验证 Evo-Harness。这意味着它的失败分布里有更多"流程走不对"的成分——这正是反思能提炼出可复用操作序列的场景。我们换到 TB4 以后，失败更多是"这个任务独有的 bug 没找到"，反思自然只能产出实例级诊断。**这是方法假设与任务特性的错配，不是实现 bug。**

## 2. 两条流程

### 我们跑的版本

```mermaid
flowchart TD
    A["任务 N 开始"] --> B["读取 harness.md"]
    B --> C["整段拼接到任务说明末尾"]
    C --> D["mini-swe-agent 执行<br/>150 步 / 90 分钟 / $2"]
    D --> E{"独立 verifier 打分"}
    E -->|"通过"| F["记录 reward = 1"]
    E -->|"失败"| G["只取 verifier 输出 + 最后 8 条命令"]
    G --> H["LLM 反思<br/>产出至多 2 条 TRIGGER / ACTION / WHY"]
    H --> I["无条件追加到 harness.md<br/>超过 4000 字符丢最旧段落"]
    I --> J["任务 N+1"]
    F --> J
```

关键特征：**反馈窄、结构松、注入粗、无验收**。

### 论文的版本

```mermaid
flowchart TD
    A["任务批次 B_i"] --> B["当前 harness 注入 Agent 运行时<br/>影响 planning / acting / verifying / recovery"]
    B --> C["Agent 单次执行任务"]
    C --> D{"结果与反馈"}
    D -->|"失败或负反馈"| E["执行反思<br/>完整上下文：指令、轨迹、观测、工具输出、反馈"]
    D -->|"成功"| F["跳过反思"]
    E --> G["候选记忆<br/>lesson + trigger + evidence + scope_hint"]
    F --> H["Harness 演化器<br/>合并、去重、写入现有 harness"]
    G --> H
    H --> I["分层 harness<br/>general skill（跨任务）+ topic skill（同类任务）"]
    I --> A
```

关键特征：**反馈完整、结构显式、分域存储、有合并策略**。

## 3. 逐项差异

| 环节 | 我们的实现 | 论文 | 造成什么后果 |
|---|---|---|---|
| 反思输入 | verifier 输出 + 最后 8 条命令 | 完整执行上下文（指令、轨迹、观测、工具输出、反馈） | 只能看到"结果错在哪"，看不到"过程为什么错" |
| 记忆结构 | 自由文本 | `lesson / trigger / evidence / scope_hint` 四元组 | 没有 scope 就无法判断适用范围 |
| 分域 | 无 | general skill + topic skill 两层 | 跨域污染：HTML 经验注入到 WAL 恢复题 |
| 注入位置 | 任务说明末尾 | Agent 运行时（规划、执行、验证、恢复） | 建议被当成额外需求，与任务要求冲突 |
| 注入粒度 | 整个 harness 全量 | 按 scope 检索相关内容 | 无关条目占用上下文、误导工具选择 |
| 合并策略 | 无条件追加 | 演化器合并去重 | 重复经验堆积，有效经验被挤掉 |
| 淘汰策略 | 超过 4000 字符丢最旧 | 由 harness 结构决定 | 同一题在不同时刻看到不同版本，处理不一致 |
| 验收门槛 | 无 | 通过实验分析哪些更新真正有效 | 错误经验无法被拦截 |
| 评估协议 | 每题 1 次、15 题、单一顺序 | 五个 benchmark、顺序任务流 | 单次方差就能翻转结果，效应无法与噪声分离 |

## 4. 三个最关键的缺口

**缺 scope。** 最根本的一条。没有"这条经验属于哪类任务"的标注，选择性注入就不可能实现，而选择性注入正是"迁移"和"干扰"的分界线。

**缺验收。** 论文把 harness 更新当作需要验证的假设；我们是"失败就写进去"。没有验收门槛，harness 只会单调增长，质量不可避免地下降。

**缺可分离的评估。** 每题只跑一次，`html-js-filter` 在 harness 为空时也翻转了——说明单次结果里有相当比例是噪声。在这种信噪比下，任何小于 20 个点的效应都测不出来。

## 5. 这个仓库现在能证明什么

不能说"复现了 Evo-Harness"。能说的是：

1. **能搭起可复现的评测管线**：Harbor + mini-swe-agent + TB4，固定预算、逐题记录 token/费用/耗时，附带 provenance（版本、镜像、任务文件哈希、job ID）。
2. **能跑出干净基线**：19 题逐题标注有效 / 截断 / 无效，而不是把截断当失败。
3. **能实现一个方法骨架并诚实报告负结果**：14 组配对，10 → 6，翻盘 0、退步 4。
4. **能定位失败原因**：四层机制问题 + 两个实验设计问题，并对齐到论文的具体组件。

第 4 点通常比第 2 点更难，也更少见于学生项目。

## 6. 如果继续做

按优先级，前两步各几十行改动：

1. **scope 字段 + 按 category 过滤注入**（把"迁移"和"干扰"分开）
2. **注入改到 system prompt**（从"要求"变回"背景"）
3. **去重 + 按 scope 分桶淘汰**，替掉"丢最旧"
4. **加验收门槛**：新经验先在 1–2 道留出题上验证有效再写入（GEPA 的 minibatch 接受思路）
5. **每题 3 次重复**，配对比较，把效应和方差分开

做完 1–2 之后重跑同一组 15 题，才有资格讨论"Evo-Harness 在 TB4 上行不行"。现在只能说：**这一版实现无效，且原因已经定位。**

## 7. No Propose：论文自己的消融说明了什么

论文对它的定义只有一句：**No Propose removes solver-side proposal of candidate memories.**

正常流程是两段式：执行结束 → proposer 反思出候选记忆（lesson / trigger / evidence / scope_hint）→ evolver 拿候选记忆与当前 harness 决定 Add / Merge / Revise / Skip。No Propose 摘掉第一段，evolver 直接面对原始执行上下文，退化成一段式直更。

它和 No Evolve 构成一条消融阶梯：

```
No Evolve  <  No Propose  <  Evo-Harness（完整）
  不更新        少一级              两段式
```

| 设置 | CL-Bench | SWE-bench Lite |
|---|---:|---:|
| No Evolve | 29.54 | 63.67 |
| No Propose | 33.28 | 65.33 |
| 完整 | 34.02 | 67.00 |

读法：No Propose 已吃到大部分收益，说明**收益主要来自"把上下文编译进 harness"这个动作本身**，结构化四元组只再贡献 0.7–1.7 个点。论文的措辞是两者互补，但权重并不对等。

保留意见：论文没有展开 No Propose 里 evolver 拿到的是原始轨迹还是简化摘要。如果它拿的仍是完整上下文，那"少了 proposer"只等于少一次 LLM 调用，这条消融的解释力要打折。

## 8. 用论文自己的证据解释我们的负结果

三个前提我们同时不满足，这不是实现 bug：

**前提一：批级更新。** 论文明确写 $|B_i| = 1$ 时方法退化成只有 task-type 更新，跨任务模式无从产生。算法里 `CompileCrossTask` 的输入是"本批所有任务的候选记忆集合"，只有批级更新才能横向比较。我们每题一跑、跑完立刻更新，等于删掉了半个方法。

**前提二：solver 能力。** DeepSeek V4.1 Flash 在 TB4 上是 33.8%（独立评测）/ 42.3%（厂商口径）：开源模型里最强，绝对能力属于中游。而论文 RQ1 显示收益随 solver 能力单调上升——Opus 4.6 在深 CL-Bench 上 +4.5（PTE 类别 +9.8），Kimi-K2.5 只有 +1.1，GPT-OSS 只有 +0.8。弱 solver 的预期收益本来就接近零。

**前提三：任务类型。** 论文的 CL-Bench 分类里，PTE（程序性任务执行）每个模型都提升、最高 +9.8；而 EDS（经验发现与仿真）在 Opus 4.6 上是 **−2.5**、GPT-OSS 是 −1.0。TB4 的失败更接近 EDS（长程、任务独有、探索性强），而不是 PTE。**我们把方法搬到了论文自己报告"可能为负"的任务类型上。**

## 9. 四条最值钱的可解释性发现

**① 弱 solver 会被 harness 拖累。** SWE-bench Lite 上，Sonnet 当 solver 时 No-Evolve 58.0，Same 演化 55.3、Cross 演化 55.7——两个都低于不演化；而 Opus 当 solver 时是 70.7 → 75.3 / 76.0。harness 要求 solver 有能力理解并执行这些指导。我们观察到的 10 → 6 与此同类。

**② 模型自评比不更新更差。** Self-Generated 反馈把 CL-Bench 从 29.54 拉到 27.96、SWE 从 63.67 拉到 61.67。没有外部证据锚定的自我判断会写入错误经验。我们用的是 verifier 输出（Standard 级），没踩这个坑——所以问题不在反馈来源。

**③ 反馈越详细未必越好。** SWE-bench 上 Minimal（只有通过/失败）67.33 > Standard（详细报错）67.00。作者解释是详细报错让 harness 过度贴合具体失败。这正好解释我们的 harness 为什么全是实例级诊断（某字段算错、某依赖太慢）：给的信息越细，反思越往单个 bug 上钻。

**④ general / topic 的权重取决于任务同质性。** CL-Bench 靠 topic（33.70 vs general 30.28），SWE 靠 general（66.67 vs topic 64.33）。没有普适答案。

## 10. 这对"复现"意味着什么

严格对齐论文需要同时满足：批级更新（每批 5–10 题）、程序性任务为主的 benchmark（TB2）、以及与论文同量级的 solver。三条我们目前只有第一条勉强可做。

现实路径是把它标注为**低资源变体**：保留 DeepSeek Flash 与 TB4，只验证 scope 过滤与注入位置这两个最小改动，并在报告里明确"这不是论文设定的复现"。在此之前，任何"Evo-Harness 在 TB4 上无效"的说法都不成立。
